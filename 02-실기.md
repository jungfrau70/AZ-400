## Lab 2. Azure Repos 브랜치 정책과 PR

1. Repos → 빈 저장소 `az400-hello`에 푸시
   ```powershell
   git remote add origin https://dev.azure.com/<org>/AZ400-Lab/_git/az400-hello
   git push -u origin main
   ```
2. **Repos → Branches → main → Branch policies**
   - Require a minimum number of reviewers: **1**, *Allow requestors to approve their own changes* 체크(혼자 실습용)
   - **Check for linked work items**: Required
   - **Check for comment resolution**: Required
   - **Limit merge types**: Squash merge만 허용
   - (Lab 4 이후) **Build validation**: CI 파이프라인 추가
3. 기능 브랜치 작업
   ```powershell
   git checkout -b feature/home-message
   # HomeController.java 반환 문자열 수정 → "Hello AZ-400!"
   # 테스트(SpringboothelloworldApplicationTests)도 필요 시 수정
   git commit -am "Change home message #<스토리ID>"
   git push -u origin feature/home-message
   ```
4. PR 생성 → 작업 항목 연결 → 리뷰 주석 작성 후 Resolve → **Squash commit**으로 완료, *Delete source branch* 체크
5. main 이력에 커밋이 1개로 합쳐졌는지 `git log --oneline` 으로 확인

✅ **확인 포인트**: 정책 미충족 시 *Complete* 버튼 비활성. `Project settings → Repositories → Security`에서 **Bypass policies when completing pull requests** 권한 위치 확인

### 3-3. 실수로 커밋한 비밀 제거 (연습용 별도 클론에서)
```powershell
# 1) 가짜 비밀 커밋
"db.password=P@ssw0rd123" | Add-Content src/main/resources/application.properties
git commit -am "oops"
# 2) 실제 상황이라면 → 가장 먼저 비밀번호를 폐기/교체(rotate)!
# 3) 이력 정리 (pip install git-filter-repo)
git filter-repo --replace-text <(echo 'P@ssw0rd123==>***REMOVED***')   # Bash 문법
# PowerShell: 'P@ssw0rd123==>***REMOVED***' | Out-File -Encoding ascii replace.txt; git filter-repo --replace-text replace.txt
git push --force --all
```

✅ **확인 포인트**: 이력을 지워도 이미 클론/포크된 사본에는 남음 → **교체(rotation)가 우선**

## Lab 4. CI 파이프라인 (Azure Pipelines YAML)

### 4-1. JaCoCo 커버리지 플러그인 추가 (`pom.xml`의 `<build><plugins>` 안)
```xml
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.14</version>
  <executions>
    <execution><goals><goal>prepare-agent</goal></goals></execution>
    <execution><id>report</id><phase>verify</phase><goals><goal>report</goal></goals></execution>
  </executions>
</plugin>
```
> Java 25 지원 버전은 Maven Central에서 최신 jacoco 버전을 확인하세요.

### 4-2. `azure-pipelines.yml` (저장소 루트)
```yaml
trigger:
  branches: { include: [ main ] }
  paths:    { exclude: [ '*.md' ] }

pool:
  vmImage: ubuntu-latest

variables:
  MAVEN_CACHE_FOLDER: $(Pipeline.Workspace)/.m2/repository
  MAVEN_OPTS: -Dmaven.repo.local=$(MAVEN_CACHE_FOLDER)

steps:
- checkout: self
  fetchDepth: 1                      # shallow clone

- task: JavaToolInstaller@0
  inputs:
    versionSpec: '25'
    jdkArchitectureOption: x64
    jdkSourceOption: PreInstalled

- task: Cache@2
  displayName: Cache Maven repo
  inputs:
    key: 'maven | "$(Agent.OS)" | **/pom.xml'
    restoreKeys: |
      maven | "$(Agent.OS)"
    path: $(MAVEN_CACHE_FOLDER)

- script: ./mvnw -B verify $(MAVEN_OPTS)
  displayName: Build & Test

- task: PublishTestResults@2
  condition: succeededOrFailed()
  inputs:
    testResultsFormat: JUnit
    testResultsFiles: '**/surefire-reports/TEST-*.xml'

- task: PublishCodeCoverageResults@2
  inputs:
    summaryFileLocation: '$(System.DefaultWorkingDirectory)/target/site/jacoco/jacoco.xml'

- task: CopyFiles@2
  inputs:
    contents: 'target/*.jar'
    targetFolder: $(Build.ArtifactStagingDirectory)
    flattenFolders: true

- task: PublishPipelineArtifact@1
  inputs:
    targetPath: $(Build.ArtifactStagingDirectory)
    artifact: drop
```

### 4-3. 실행
1. Pipelines → New pipeline → Azure Repos Git → `az400-hello` → **Existing Azure Pipelines YAML file** → 실행
2. 두 번째 실행에서 Cache 단계가 *Cache restored* 로 바뀌고 빌드 시간이 줄어드는지 확인
3. 실행 결과의 **Tests**, **Code Coverage** 탭 확인
4. Lab 2의 main 브랜치 정책에 **Build validation**으로 이 파이프라인 추가 → PR에서 자동 실행 확인

## Lab 6. IaC — Bicep

### 6-1. `infra/main.bicep`
```bicep
@description('전역 고유 웹앱 이름')
param appName string
param location string = resourceGroup().location
@description('az webapp list-runtimes 로 확인한 Java 메이저 버전')
param javaVersion string = '25'

var linuxFx = 'JAVA|${javaVersion}-java${javaVersion}'

resource law 'Microsoft.OperationalInsights/workspaces@2023-09-01' = {
  name: 'law-${appName}'
  location: location
  properties: { sku: { name: 'PerGB2018' }, retentionInDays: 30 }
}

resource appi 'Microsoft.Insights/components@2020-02-02' = {
  name: 'appi-${appName}'
  location: location
  kind: 'web'
  properties: { Application_Type: 'web', WorkspaceResourceId: law.id }
}

resource plan 'Microsoft.Web/serverfarms@2023-12-01' = {
  name: 'plan-${appName}'
  location: location
  kind: 'linux'
  sku: { name: 'S1' }            // 배포 슬롯은 Standard 이상
  properties: { reserved: true }
}

var appSettings = [
  { name: 'APPLICATIONINSIGHTS_CONNECTION_STRING', value: appi.properties.ConnectionString }
  { name: 'ApplicationInsightsAgent_EXTENSION_VERSION', value: '~3' }   // Java 자동 계측
  { name: 'SERVER_PORT', value: '80' }
]

resource web 'Microsoft.Web/sites@2023-12-01' = {
  name: appName
  location: location
  identity: { type: 'SystemAssigned' }
  properties: {
    serverFarmId: plan.id
    httpsOnly: true
    siteConfig: {
      linuxFxVersion: linuxFx
      healthCheckPath: '/home'
      appSettings: appSettings
    }
  }
}

resource staging 'Microsoft.Web/sites/slots@2023-12-01' = {
  parent: web
  name: 'staging'
  location: location
  properties: {
    serverFarmId: plan.id
    siteConfig: { linuxFxVersion: linuxFx, appSettings: appSettings }
  }
}

output webAppName string = web.name
output principalId string = web.identity.principalId
```

### 6-2. 로컬에서 what-if → 배포
```powershell
az deployment group what-if -g $RG -f infra/main.bicep -p appName=$APP
az deployment group create  -g $RG -f infra/main.bicep -p appName=$APP
```

### 6-3. 파이프라인에서 IaC 실행
1. **Project settings → Service connections → New → Azure Resource Manager → Workload identity federation (automatic)** → 범위: 리소스 그룹 `rg-az400-lab`, 이름 `sc-az400`
2. `infra-pipeline.yml`
   ```yaml
   trigger:
     branches: { include: [ main ] }
     paths:    { include: [ infra/* ] }
   pool: { vmImage: ubuntu-latest }
   variables:
     rg: rg-az400-lab
     appName: <위에서 만든 $APP 값>
   stages:
   - stage: Preview
     jobs:
     - job: whatif
       steps:
       - task: AzureCLI@2
         inputs:
           azureSubscription: sc-az400
           scriptType: bash
           scriptLocation: inlineScript
           inlineScript: az deployment group what-if -g $(rg) -f infra/main.bicep -p appName=$(appName)
   - stage: Apply
     dependsOn: Preview
     jobs:
     - deployment: apply
       environment: infra-prod          # 여기에 승인(Approval) 설정
       strategy:
         runOnce:
           deploy:
             steps:
             - checkout: self
             - task: AzureCLI@2
               inputs:
                 azureSubscription: sc-az400
                 scriptType: bash
                 scriptLocation: inlineScript
                 inlineScript: az deployment group create -g $(rg) -f infra/main.bicep -p appName=$(appName)
   ```
   > deployment 작업은 기본적으로 소스를 체크아웃하지 않으므로 `- checkout: self` 필요

✅ **확인 포인트**: Bicep의 `sku`를 `S2`로 바꿔 what-if 출력에서 `~ Modify` 확인. `--mode Complete`의 의미(템플릿에 없는 리소스 삭제) 이해

## Lab 7. 멀티 스테이지 CD (슬롯 배포 + 스왑 + 승인)

### 7-1. Environment 구성
**Pipelines → Environments**
- `staging`: 검사 없음
- `production`: **Approvals**(본인), **Branch control**(`refs/heads/main`만 허용), **Exclusive lock**

### 7-2. 단계 템플릿 `templates/deploy-steps.yml`
```yaml
parameters:
- name: slot
  type: string
steps:
- task: AzureWebApp@1
  inputs:
    azureSubscription: sc-az400
    appType: webAppLinux
    appName: $(appName)
    deployToSlotOrASE: true
    resourceGroupName: $(rg)
    slotName: ${{ parameters.slot }}
    package: $(Pipeline.Workspace)/drop/*.jar
- script: |
    for i in 1 2 3 4 5 6; do
      code=$(curl -s -o /dev/null -w "%{http_code}" "$(url)/home") && [ "$code" = "200" ] && exit 0
      sleep 10
    done
    exit 1
  displayName: Smoke test
```

### 7-3. `azure-pipelines.yml`을 멀티 스테이지로 변경
```yaml
trigger:
  branches: { include: [ main ] }

variables:
  rg: rg-az400-lab
  appName: <$APP 값>

stages:
- stage: Build
  jobs:
  - job: build
    pool: { vmImage: ubuntu-latest }
    steps:
    # (Lab 4의 빌드 단계 그대로)
    - task: JavaToolInstaller@0
      inputs: { versionSpec: '25', jdkArchitectureOption: x64, jdkSourceOption: PreInstalled }
    - script: ./mvnw -B verify
    - task: CopyFiles@2
      inputs: { contents: 'target/*.jar', targetFolder: $(Build.ArtifactStagingDirectory), flattenFolders: true }
    - task: PublishPipelineArtifact@1
      inputs: { targetPath: $(Build.ArtifactStagingDirectory), artifact: drop }

- stage: Staging
  dependsOn: Build
  variables:
    url: https://$(appName)-staging.azurewebsites.net
  jobs:
  - deployment: deployStaging
    pool: { vmImage: ubuntu-latest }
    environment: staging
    strategy:
      runOnce:
        deploy:
          steps:
          - checkout: self                       # 템플릿 파일 사용을 위해
          - template: templates/deploy-steps.yml
            parameters: { slot: staging }

- stage: Production
  dependsOn: Staging
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: swap
    pool: { vmImage: ubuntu-latest }
    environment: production                      # 여기서 승인 대기
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureAppServiceManage@0
            inputs:
              azureSubscription: sc-az400
              action: Swap Slots
              webAppName: $(appName)
              resourceGroupName: $(rg)
              sourceSlot: staging
              swapWithProduction: true
```
> 템플릿 참조(`template:`)는 컴파일 시 확장되므로 실제로는 checkout 없이도 동작합니다. 위 checkout은 스크립트가 저장소 파일을 쓸 때를 대비한 예시입니다.

### 7-4. 검증
1. 코드 수정 → main 푸시 → Staging 배포 후 `https://<app>-staging.azurewebsites.net/home` 확인
2. Production 단계 승인 대기 → 승인 → 스왑 → `https://<app>.azurewebsites.net/home` 확인
3. **롤백 연습**: 같은 Swap 작업을 다시 실행 → 이전 버전 복귀 (Blue-Green)
4. 포털 → Web App → Deployment slots → **Traffic %** 를 staging 20%로 설정 → 카나리 체험

✅ **도전 과제**: `production` Environment의 Branch control 때문에 feature 브랜치에서 수동 실행 시 Production 단계가 차단되는지 확인

### 8-4. `.github/workflows/cicd.yml`
```yaml
name: cicd
on:
  push: { branches: [ main ] }
  pull_request: { branches: [ main ] }
  workflow_dispatch:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix: { java: [ '25' ] }
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-java@v4
      with: { distribution: temurin, java-version: '${{ matrix.java }}', cache: maven }
    - run: ./mvnw -B verify
    - uses: actions/upload-artifact@v4
      with: { name: app, path: target/*.jar }

  deploy:
    if: github.ref == 'refs/heads/main'
    needs: build
    runs-on: ubuntu-latest
    environment: production
    concurrency: { group: production, cancel-in-progress: false }
    permissions:
      id-token: write          # OIDC 토큰
      contents: read
    steps:
    - uses: actions/download-artifact@v4
      with: { name: app }
    - uses: azure/login@v2
      with:
        client-id: ${{ vars.AZURE_CLIENT_ID }}
        tenant-id: ${{ vars.AZURE_TENANT_ID }}
        subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
    - uses: azure/webapps-deploy@v3
      with:
        app-name: ${{ vars.APP_NAME }}
        slot-name: staging
        package: '*.jar'
    - run: az webapp deployment slot swap -g rg-az400-lab -n ${{ vars.APP_NAME }} --slot staging --target-slot production
```

### 8-5. 검증
- 푸시 → build 완료 후 deploy가 **Waiting for review** → 승인 → 배포
- 실패 실험: federated credential의 subject를 `...:ref:refs/heads/main`으로 바꾸면 Environment 사용 시 로그인 실패 (`AADSTS700213: No matching federated identity record`) → **subject는 environment 사용 여부에 따라 달라짐**

✅ **도전 과제**: build 작업을 **reusable workflow**(`on: workflow_call`)로 분리하고 호출
